# MITGCM-BOM P5.5 scientific aggregate contract

Status: **FROZEN BEFORE THE FIRST P5-SA-G99 CANDIDATE RUN**

This contract implements section 11 of `SCIENTIFIC_ACCEPTANCE_PLAN.md`. It
does not amend that frozen plan, any P5.1--P5.4 scientific criterion, fixture,
formula, oracle, tolerance or expected result.

## 1. Candidate and predecessor identity

One invocation admits one clean exact candidate commit. The candidate must
descend from the exact annotated `MITGCM-BOM-v0.5` release:

- tag object: `f16e2345cbe596f37fe3434d1b2f23f85ff0ba74`;
- peeled commit: `1f48a75d4865fa6d5235a4db306e8abe31534f3e`.

P5.1, P5.2, P5.3 and P5.4 run directly on that candidate. The released Phase
4 predecessor is not historical evidence reuse: its complete 689-row gate is
replayed on the same candidate in a fresh shared clone. The clone contains the
exact v0.4 tag object, omits the v0.5 tag ref, uses predecessor mode and may
extend source admission only for the frozen Phase 5 scientific paths. It may
not change a Phase 4 test, row name, row order or count.

### 1.1 D001 and the specialised F01 transaction contract

P5-D001's general two-commit rule and the later, specialised P5-F01 contract
must be applied together. F-SPRING, J01, P01/P02, O01, R01 and L01 are
trajectory/integration acceptance cases and retain the two-or-more-commit
rule. The F-EVENT birth/cancel/death subcases, F-COAST and F-COMBINED are
deliberately frozen one-step transaction/terminal probes in
`P5.4_TEST_CONTRACT.md`; their specialised one-step definitions control for
commit count. They remain positive production launches and must still satisfy
normal completion plus every exact preflight, publication, event, budget and
rollback criterion in that contract.

This is a specific-over-general reconciliation recorded before the first
P5-SA-G99 candidate output. It neither changes the frozen words nor turns a
one-step integration trajectory into scientific evidence. Treating those
five probes as two-step cases would silently change the already-frozen F01
fixtures and expected event inventories, which this contract forbids.

## 4. Freshness, isolation and evidence

Every child receives a unique aggregate-derived ID and fresh external build,
run, replay and artifact roots. Existing roots are fatal. Native manifests,
source heads, clean-state records and independent PASS reports are verified
before registration. No verification mods directory may contain a production
`bom_*.F` override. No foreign-project path or dependency is admitted.

The aggregate writes ordered row, provenance, case, reference-lock and
expected/actual inventories. Its independent auditor executes before a
sorted SHA-256 manifest is generated outside the evidence root and published
back into it. A second independent scientific exit audit validates that
manifest and P5-D001--P5-D021 traceability from a separate fresh root.

The gate snapshots source tags before and after execution. It creates no tag.

## 5. Failure semantics

The current group is classified as build/package, input/provenance, runtime,
JULIA physics, PAPER2024 physics, integration/I/O, restart/MPI or reference
tooling. A nonzero child or audit result records `FAIL` (or `BLOCKED` only for
a genuinely unavailable required dependency), preserves all partial roots,
publishes a failure manifest, makes the failure evidence read-only and never
writes a TOTAL PASS or invokes the exit audit. A retry always uses a new ID.

Expected-failure scientific cases count as PASS only when their frozen failure
phase, prepublication boundary and rollback checks all pass in the native
gate.

## 6. Decision boundary

P5-SA-G99 plus the independent exit audit can decide only scientific
acceptance on the admission platforms. It does not decide OpenMP safety,
target-server scheduler or filesystem behavior, 100,000-particle/256-rank
scale, less-than-20-percent overhead, or changed-decomposition restart. Those
remain later Phase 5 HPC work. No tag is created by P5.5.
