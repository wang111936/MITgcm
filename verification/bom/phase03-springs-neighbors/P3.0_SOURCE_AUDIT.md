## 2. Accepted v0.3 facts

The current production path has these relevant properties:

1. owner particles use compact per-tile SoA storage and exact positive 64-bit
   IDs;
2. each RK routine advances one particle at a time, then the caller commits
   that particle before moving to the next slot;
3. owner migration occurs after a complete nominal substep and is
   transactional;
4. Phase 2 samples old/new fields at exact stage times and publishes 27
   accepted diagnostics only after a successful particle trial;
5. later trial stages may use the owner tile's exchanged field overlap;
6. `bomMaxGhostTile` and `bomMaxNeighbor` exist only as unused placeholders;
7. there is no ghost-particle state, neighbor graph, spring diagnostic,
   component label or Phase 3 disk schema;
8. schema 2 deliberately fixes the main trajectory record at 48 fields for
   small verification tiles;
9. `BOM_FAIL_*` values 0--15 and `BOM_STAGE_*` values 0--8 are already stable
   and may not be renumbered;
10. the v0.3 path is proven by the exact 390-row release gate.

Finding P3-A: a coupled spring RHS cannot be added safely inside the current
per-particle RK calls. At a given K stage all particles must see the same stage
snapshot. A new ensemble-level scratch transaction is required.

## 3. Locked Julia connection behavior

`ConnectionsRadius` builds a `BallTree` and asks for all points within a
radius. `ConnectionsNearest` builds a `KDTree`, requests `neighbors+1` because
self is present, and sorts returned indices by array index. These operations
are global-memory algorithms and their indices depend on the Julia living-slot
layout rather than MITGCM-BOM global IDs.

`DeltaL(InitialConditions;k)` asks the tree for exactly `k` entries including
self, averages distances with denominator `k-1`, and takes the median of the
per-particle values. Its docstring calls these the `k` nearest neighbors, so
the code and prose disagree by one.

Finding P3-B: the Julia trees are useful as a small numerical oracle but do not
define a distributed production algorithm. P3 freezes an explicit oracle
definition using `K` non-self neighbors and global-ID tie breaks. The fixture
must also evaluate the literal locked-Julia convention and record the expected
difference when `k=K` is used.

## 4. Locked Julia spring behavior

For a pair `(i,j)`, `Raft!` and `FastRaft!` add

```text
tau * k(d) * (L/d - 1) * (x_i - x_j)
```

to particle `i` and the opposite value to `j`. The code visits only `j>i` in
Julia slot order. `HookeSpring` uses constant `k`. `BOMBSpring` uses

```text
A / (exp((d - 2*L)/0.2) + 1)
```

in the reference distance unit, which is kilometres by default. Thus the
literal smoothing scale is 0.2 km, or 200 m, for the standard environment.

The reference does not protect `d=0`, exponential overflow, non-finite
parameters or accumulated-force overflow. Its spherical distance uses the
metric at particle `i`, while the opposite update is made in the same call.
That is not a symmetric physical east/north pair geometry when the two
latitudes differ.

Finding P3-C: P3 retains the Julia law and the standard 200 m comparison case,
but makes the smoothing scale an explicit SI parameter, evaluates the logistic
without overflow, rejects unresolved zero-length pairs, and uses a canonical
symmetric pair geometry.

## 5. Force versus velocity terminology

The project manual writes a spring `F_i`, while Julia directly adds
`tau*k(d)*(L/d-1)*delta_x` to the position RHS. Under SI storage this means:

- `k` and `A`: s^-2;
- `L`, smoothing scale and cutoff: m;
- `tau`: s;
- spring contribution to drift: m s^-1.

Finding P3-D: production diagnostics are named `spring velocity`, not force.
The stateless spring-law helper may expose the acceleration-like factor, but
only `tau`-scaled east/north velocity enters the Phase 2 drift and RK rate.

## 6. Pair and MPI determinism finding

The manual requires ID-sorted accumulation and permits a cross-rank edge to be
computed independently at both owners. Recomputing an edge from owner-relative
coordinates could produce a different metric, periodic direction or rounding
order at the two ends.

Finding P3-E: every edge uses canonical low-ID/high-ID orientation, shortest
periodic displacement and one symmetric metric. Each owner computes only its
own update but derives the identical canonical magnitude and applies a sign
from its ID. Neighbor IDs are strictly increasing before accumulation. This
avoids remote force communication and makes 1/2/4-rank equality testable.

## 7. Cutoff and cell-list finding

An exact radius graph and a cell-linked list are different concerns. The graph
is mathematically defined by `d<=rCut`; the cell list is only a candidate
generator. A candidate generator may return duplicates or false positives but
the accepted graph may contain neither. Boundary equality, periodic images and
cell-face ties must be deterministic.

Finding P3-F: P3 freezes half-open cells, exact `d<=rCut`, no self edge,
one neighbor ID per owner, and final ID sort. Production rebuilds the graph at
every RK stage in Phase 3. Verlet skin reuse is deferred until a later measured
optimization and cannot enter P3.1--P3.5 silently.

## 8. Ghost and owner finding

The accepted owner exchange moves authoritative records only after a substep.
Ghost records have a different purpose and lifetime: read-only candidate state
for exactly one RK stage. Reusing the owner packet would risk committing a
ghost or carrying stale diagnostics.

Finding P3-G: ghost exchange gets an independent versioned packet and scratch
storage. It contains exact ID words, stage position, status, source rank/tile
and stage/epoch labels. Counts, capacities, packet contents and duplicate IDs
are globally validated before any ghost-ready flag is published. Ghosts never
enter owner counts, output, pickup or migration.

## 9. Ensemble transaction finding

Spring coupling means that a failure for one owner invalidates the whole stage
snapshot. Per-particle rollback is insufficient because earlier particle
slots might already have been committed.

Finding P3-H: spring-enabled RK creates complete X0/K1--K4/FINAL scratch state
for all owners. Each stage follows position build, ghost exchange, cell/graph
build, spring evaluation, Phase 2 RHS evaluation and global validation. No
authoritative position, diagnostic, graph or schedule changes until the whole
substep succeeds. Owner migration remains after that commit.

## 10. Raft and disk-schema finding

A graph connected component has no stable Julia raft identifier. Slot/rank
order is not acceptable. The v0.3 48-field record also cannot be widened
without violating its frozen small-tile layout.

Finding P3-I: the raft ID is the minimum positive global particle ID in the
accepted FINAL cutoff component; a singleton uses its own ID. Deterministic
min-label propagation continues until a global no-change result. Container
schema 3 keeps the schema-2 core record byte-for-byte and adds a required
versioned P3 sidecar for exact raft-ID words, neighbor/component counts and
spring east/north velocity.

## 11. Complexity finding

A cell list removes the unconditional all-pairs production loop, but a dense
cell can still have quadratic candidates. Wall-clock timing alone cannot prove
algorithmic structure and is noisy on WSL.

Finding P3-J: source audit rejects gather/allgather and global particle-pair
loops in `pkg/bom`; runtime counters expose owners, ghosts, cell candidates,
accepted directed neighbors, undirected edges, rebuilds and bytes. Fixed-density
fixtures require bounded candidates per owner and record serial/MPI timing.
Target-server scaling remains Phase 5.
